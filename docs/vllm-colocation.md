# 한 GPU에 vLLM 서버 여러 개 띄우기 (co-location)

검증 환경: vLLM 0.26.0, RTX PRO 6000 (96GB), `google/gemma-4-E4B-it` ×3 on GPU0.
결과: **3개 동시 서빙 성공** — GPU0 합계 79GB, 인스턴스당 ~26GB, 각 KV 314,603 tokens
(32k 요청 9.6× 동시 수용). 라우터가 3개를 같은 모델 워커로 등록해 least_connections로 분배.

## 동작하는 레시피

```
gpu_util:   0.32              # 낮게. "여유메모리 ≥ util×전체" 기동 검사를 통과해야 함
max_len:    32768             # --max-model-len. 기본 컨텍스트가 크면 KV가 '최대 길이 1개'를 못 담아 실패
extra_args: --max-num-seqs 512
            --max-num-batched-tokens 4096       # 프로파일 로짓 버퍼 축소 (아래 참고)
            --kv-cache-memory-bytes 8589934592  # KV 8GB 절대값 — util 비율 계산 우회 (핵심)
기동:        인스턴스 간 20~25초 간격 (프로파일 겹침 방지)
```

central `/api/deploy`로는 같은 `gpus: ["<worker>-0"]`에 배포를 N번 호출하면 됨 (워커가 포트를 순차 할당).

## 왜 순진한 방법은 전부 실패하는가 — 3가지 트랩

1. **util 비율만 낮추기 (0.22) → `No available memory for the cache blocks`**
   `gpu_memory_utilization`은 GPU *전체*의 비율이고, vLLM 메모리 프로파일은 GPU *전역* 사용량을
   읽는다. 인스턴스 2·3은 인스턴스 1이 이미 쓴 메모리까지 자기 오버헤드로 계산해
   `util×전체 − (남들 + 내 가중치)`가 음수 → KV 0 → 실패. util을 아무리 조정해도 단독으론 안 됨.

2. **util 높게 (0.95) + KV 절대값 → `Free memory (78 GiB) < desired util (90 GiB)`**
   0.26은 기동 시 "여유 메모리 ≥ util×전체"를 검사한다. 다른 인스턴스가 메모리를 쓰고 있으면
   높은 util은 여기서 죽는다. → **util은 낮게, KV는 절대값으로** 분리해야 둘 다 통과.

3. **어휘가 큰 모델의 프로파일 피크** — gemma-4는 vocab 262,144. 프로파일 forward에서
   `max_num_batched_tokens(기본 8192) × 262144 × 4B ≈ 8.6GB` 로짓 버퍼가 잡혀
   가중치 14.4GB + 8.6GB만으로 21GB 예산을 넘긴다. `--max-num-batched-tokens 4096`으로 절반으로.
   `--max-model-len`을 캡하면 프로파일/KV 요구도 함께 줄어듦.

## 결과 (동시성 2048, 4096요청 × 128tok)

| 구성 | req/s | tok/s | p50 | GPU util |
|---|---|---|---|---|
| gemma-4 ×1 (GPU 1장, 직접) | 73.7 | 9,433 | 20.6s | 58–72% ← **유입(API 서버) 병목** |
| gpt-oss-120b ×1 (GPU 1장, 직접) | 69.0 | 8,828 | 24.2s | 100% ← GPU 병목 |
| **gemma-4 ×3 (GPU 1장, 직접 합산)** | **119.5** | **15,290** | **14.4s** | **99–100%** ← GPU 병목 |
| gemma-4 ×3 (GPU 1장, **라우터 경유**, 수정 전) | 37.6 | 4,814 | 45.7s | (엔진은 35초에 끝났으나 클라이언트는 109초 대기) |

- ×3 직접 합산 = 단일 gemma-4의 **1.62×**, 같은 GPU의 gpt-oss-120b의 **1.73×**, 지연도 더 좋음.
- 3배가 아닌 이유: 병목이 유입 → GPU 연산으로 옮겨가 천장(100%)에 닿음. 4번째 인스턴스는 무익.

핵심 교훈: 작은 모델의 단일 인스턴스는 요청당 HTTP/토크나이즈/파싱 오버헤드(단일 uvicorn)에
막혀 GPU를 다 못 쓴다. **인스턴스(=API 서버) 수를 늘리면 GPU가 포화되며 처리량이 오르고**,
그 이후엔 GPU 연산이 진짜 천장이 된다. gemma-4의 장점은 단일 속도가 아니라
**15GB 메모리 → 한 GPU에 여러 개** 올릴 수 있는 밀도다.

## 부수 발견: 라우터가 고동시성 병목 (수정 중)

같은 엔진 3개를 라우터(:11434)로 경유하면 처리량이 **엔진 용량의 31%**(119.5 → 37.6 req/s)로
떨어졌다. 원인: 라우터→워커 reqwest 풀 `pool_max_idle_per_host(500)` < 워커당 ~680 동시 →
응답마다 초과 연결이 닫히고 다음 요청이 새 TCP+TLS(RSA-4096, 워커의 단일 프로세스 uvicorn이
서명)를 여는 churn. 직접 벤치의 httpx는 전 연결을 keep-alive해 이 비용이 없었다.
